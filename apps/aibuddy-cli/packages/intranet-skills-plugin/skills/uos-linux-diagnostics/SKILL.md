# UOS / Linux 诊断

## 先测量

确认当前确实在目标 Linux 机器上执行，再从 `/etc/os-release`、`uname -m`、`getconf GNU_LIBC_VERSION` 和已安装工具取得系统信息。命令不可用时记录缺项；不要把开发机结果当作 UOS 实测，也不要猜测国产 CPU 的指令集。

围绕具体卡顿场景采样：空闲、触发操作、结束后。优先读取指定应用及其子进程，避免反复扫描全盘。可使用已有的 `ps`、`top -b -n 1`、`free -m`、`vmstat 1 5`、`df -h`；先检查工具与参数是否受支持，输出保留必要范围。

## 按证据分流

- CPU：区分短时峰值与持续占用，查看进程/线程和负载。单核瓶颈可能被总 CPU 百分比掩盖；没有调用栈时不要指定某个函数为根因。
- 内存：关注 available、交换活动及已可访问的 OOM 记录。Linux 文件缓存占用不等于泄漏；比较多次相同操作后的增长。
- 磁盘：检查空间、inode 与 IO 等待；有 iostat 等现成工具时再补证据。不要把磁盘容量不足和带宽瓶颈混为一谈。
- UI：比较静态页面、滚动与流式输出，检查持续动画、阴影/模糊、大列表及重复布局。先用应用现有选项减少装饰效果，再验证功能反馈仍清楚。
- 启动/兼容：记录可执行文件架构、错误输出和依赖版本。若有 readelf/objdump，检查实际二进制及原生扩展的符号版本；包依赖声明不能单独证明 glibc 兼容。仅对可信程序使用会执行代码的诊断方式。
- 图形：依据应用日志和现有图形信息判断驱动/合成问题。硬件加速开关可能改善或恶化性能，只有可比较证据时才提出临时对照测试。

## 优化与验证

优先减少应用自身的无效工作。用户授权修复后，每次只改变一个可回退因素，记录原值，以同一操作、数据量和采样方式复测响应时间与资源占用。系统服务、内核参数、清理文件或终止进程不作为通用提速步骤。

不自动运行 apt/pip/npm 安装、下载驱动或上传日志。缺少 profiler 时说明能确认的范围。交付实际测量、候选原因、最小措施、恢复方式与待验证项；没有前后测量就不宣称提升百分比。
