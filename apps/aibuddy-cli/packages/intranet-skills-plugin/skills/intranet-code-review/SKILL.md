# 本地代码审查

## 工作顺序

1. 读取项目指令、当前差异和已有测试入口，明确审查基线。保留用户未提交的修改；审查请求只产出发现，修复请求才改代码。
2. 从变更入口沿调用方、状态所有者、异常路径追踪。先搜符号及全部调用方，再阅读相关代码，避免把整个仓库送入上下文。
3. 对每个候选缺陷写清触发输入、实际路径、错误结果和受影响的功能；仅凭风格偏好或未证实的可能性不列为缺陷。
4. 性能问题先辨认成本来源：重复计算、同步 IO、频繁重渲染、无界缓存、全量扫描、轮询或动画。说明发生频率、数据规模及成本，利用已有测量入口验证。
5. 用户要求修复时，优先在共同入口做最小修改并运行能重现问题的检查；不要删除校验、取消、权限或平台兼容分支来换取速度。

## 检查要点

- 身份键、路径、窗口或会话边界是否混用；异步结果是否覆盖较新的状态。
- 列表或流式输出增长后，是否重复处理全部历史；缓存是否有正确的失效条件。
- 超时、重试、取消后资源是否释放；失败结果是否被误当成功。
- 构建或测试脚本是否会联网、安装依赖或接触业务环境。优先运行现有本地检查；工具缺失时报告限制，不自动下载替代品。

## 交付

按影响排序给出少量可行动的发现，每项包含文件与行号、触发条件、证据和建议。区分确认缺陷与待测假设，记录检查命令及实际结果。没有发现时直说，并列出关键未验证路径；不把“构建通过”写成“UOS 实机性能已改善”。
