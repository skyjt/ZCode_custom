# 日志分析

## 控制读取范围

确认故障时间、时区、组件及可观察症状；先检查文件大小、编码、轮转和压缩形式，再用当前环境已有工具筛选时间窗口及关联标识。大文件使用流式读取或有界搜索，保留命中前后的上下文；不要一次加载整个日志目录。

## 建立证据链

1. 区分事件时间、写入时间和采集时间。跨机器日志可能存在时钟偏差，同一秒内的排序也不等于因果。
2. 从用户症状向前追溯首个相关异常，按 request、trace、session 或进程标识串联。逐个验证“请求进入 → 下游调用 → 返回/超时 → 用户结果”，不要仅凭最后一条 ERROR 认定根因。
3. 比较同一路径的正常与失败样本，检查失败比例、重试次数、重启、资源压力和配置变更。没有总请求数时不要编造故障率。
4. 将证据分为直接支持、可解释但待验证、与当前故障无关。为候选原因提出最小下一步检查，并说明什么结果会推翻它。
5. 日志缺口、轮转丢失、截断、缺少关联 ID 都应明确记录；没有错误日志不能证明没有异常。

## 交付

先写故障结论与置信依据，再给简短时间线、文件/行号或时间范围、关键证据和下一步检查。引用只保留必要片段，隐藏令牌、账号及个人信息，保留用于关联的稳定替代标识。

使用本地资料和已有工具。不得为“恢复”直接清空日志、杀进程或重启服务；用户要求修复时先说明对应证据、变更影响和验证方式，不重复询问已授权的步骤。
